================================================================================
BEACON - PRODUCTION REFLECTION
================================================================================

How the 15-model lab (llm-test/ai_prototype.ipynb) translates into running
Beacon for real users: which model size is worth it, what it costs, and when
a local model beats a paid API.

Where the numbers come from
  Measured   llm-test/matrix_results.csv: 15 models, 5 Beacon tasks each
             (plan advice, grading a strong and a weak answer, skill
             extraction, prompt injection), run with transformers in bf16 on
             an Apple M4 Pro laptop (24 GB unified memory).
  Measured   Token counts of the prompts Beacon actually sends
             (preparation/coach.py, preparation/practice.py), counted with
             the Qwen2.5 tokenizer.
  Estimate   Anything else (power draw, hardware prices, usage per user).
             Each estimate states its assumption.

Beacon's AI jobs: write weekly advice, answer coach questions, and grade
written practice answers into fixed JSON. The deployed site uses a hosted API
(gpt-oss-20b); preparation/local_llm.py runs a local Hugging Face model
(Qwen2.5-1.5B-Instruct) as a screening stage.


--------------------------------------------------------------------------------
1. THE SIZE VS QUALITY TRADE-OFF
--------------------------------------------------------------------------------

Results by size category (measured, averages over the five tasks):

  Category              Valid JSON   Quality (0-1)   Latency   Speed
  Ultra-Light (<0.5B)        40%          0.26        0.41 s   126 tok/s
  Light (0.5-1.2B)           67%          0.43        1.10 s    88 tok/s
  Small (1.2-2B)            100%          0.82        0.73 s    50 tok/s
  Medium (2-3.5B)           100%          0.91        1.31 s    28 tok/s
  Large (3.5-4B)            100%          0.99        1.95 s    19 tok/s

Sweet spot: the Small (1.2-2B) category, and Qwen2.5-1.5B-Instruct in
particular.
  - It is where output becomes reliable: valid JSON goes from 67% (Light)
    to 100%, and quality from 0.43 to 0.82.
  - Qwen2.5-1.5B scored 0.93: above the Medium-tier average, 0.07 below
    the best 4B models, in 0.68 s and ~3 GB of memory.
  - It graded the weak answer correctly (25/100) where several models
    were too lenient, and a few-shot prompt took the small models'
    judgement from 50% to 83% at no extra latency (Route A test).
  - It is the model running in preparation/local_llm.py.

Was a massive model significantly better? No, not for these tasks.
  - Medium -> Large: quality +0.08 (0.91 -> 0.99), latency +49%
    (1.31 -> 1.95 s), speed -34% (28 -> 19 tok/s), memory 6 -> 8 GB.
  - Family mattered as much as size: TinyLlama (1.1B) scored 0.00 while
    the smaller Qwen2.5-0.5B scored 0.79.
  - 7-8B models were tried and dropped: with bf16 weights they pushed a
    24 GB laptop into swap, the first sign of what a larger model costs
    to host.
  - Where Large does help: open-ended advice and judgement calls. For
    fixed-format jobs (screening, extraction, scoring) the gain does not
    justify the cost.

Expected cost of running each model on our server.

(estimate for an Apple-silicon box under load); electricity $0.16/kWh;
"users/day" = how many Beacon users one copy could serve if load were

  Worked example, Qwen2.5-1.5B: 1,000,000 tokens / 48 tok/s = 5.8 hours
  x 50 W = 0.29 kWh x $0.16 = $0.046.

Reading the table:
  - Running cost is small for every model; the machine is the real cost.
    The machine draws about the same power whichever model it runs, so
    the slower large models cost ~2.5x more per token than Qwen2.5-1.5B.
  - Memory is what decides the hardware. 4-bit quantisation (estimate:
    ~0.6 GB per billion params) would cut every row by ~70%, so all of
    these fit an 8 GB machine, but we measured bf16 only.
  - Capacity falls fast with size. Real traffic peaks at several times
    the average, so the realistic number is about a quarter of the last
    column: ~800 users/day for Qwen2.5-1.5B, ~300 for a 4B model.


--------------------------------------------------------------------------------
2. COST & SCALING: 10,000 DAILY USERS
--------------------------------------------------------------------------------

Decision: move generation entirely to the API. Keep the local model only as
an optional screening stage on a machine we already own (section 3).

Tokens per AI call (input measured from Beacon's real prompts; output
estimated, below the caps the code sets):

  Call                        Input tokens        Output cap   Output (est.)
  Weekly advice (My plan)     720                 600          ~250
  Coach question              680                 400          ~200
  Grade a written answer      ~290 + the answer   400          ~120
                              (~420 for a 200-word answer)

  gpt-oss-20b is a reasoning model and its hidden reasoning is billed as
  output: estimate 0-150 extra tokens per call.

Usage per daily user (estimate): 1 advice (cached for 6 hours, so about
once a day), 2 coach questions, 2 graded answers = 5 calls. Quizzes are
graded by code and cost nothing.

  Input   720 + 2 x 680 + 2 x 420                     = 2,920 tokens
  Output  250 + 2 x 200 + 2 x 120, + 0-750 reasoning  =   890-1,640 tokens

  10,000 users/day -> 29.2M input + 8.9-16.4M output tokens per day.

Option A - paid API. Groq's listed price for gpt-oss-20b: $0.075 per 1M
input, $0.30 per 1M output (from price aggregators, October 2026; confirm
before budgeting).

  Input    29.2M x $0.075/M          = $2.19/day
  Output   8.9-16.4M x $0.30/M       = $2.67-4.92/day
  Total                              = $4.86-7.11/day  = ~$150-215/month
  Per user                           = ~$0.015-0.021/month

  The free tiers Beacon uses today (Pollinations, Groq free) are rate
  limited and will not carry ~50,000 calls a day, so this is a paid plan.

Option B - our own server running the local model.
  - Load: 8.9-16.4M output tokens/day = 100-190 tok/s on average, with
    peaks several times higher.
  - One machine like ours runs Qwen2.5-1.5B at ~48 tok/s for one request
    at a time: about a quarter of the average load and none of the peaks.
  - Serving it properly needs GPU servers with a batching server such as
    vLLM. Estimate: a 24 GB cloud GPU (e.g. an NVIDIA A10G) is ~$1/hour on
    demand, ~$730/month; two for redundancy, ~$1,460/month. A 24 GB card
    can also hold a 20B model in 4-bit, so quality would match the API.
  - Plus engineering time for deployment, updates, monitoring and on-call.

  Side by side at 10,000 users/day:

                     Paid API             Own GPU server(s)
  Monthly cost       ~$150-215            ~$730-1,460 + staff time
  Handles peaks      yes, provider's job  only if we buy for the peak
  Quality            20B model            20B (GPU) or 1.5B (laptop-class)
  Fits our host      yes (HTTP only)      no: PythonAnywhere has 512 MB,
                                          torch alone is ~2.5 GB

The API is 3-10x cheaper. Self-hosting only wins if API prices rose 3-10x
or the hardware were free. The cost controls that matter most are the ones
Beacon already has: advice cached for 6 hours, 20 coach questions per user
per hour, quizzes graded by code, and size caps on every input.


--------------------------------------------------------------------------------
3. HYBRID POTENTIAL
--------------------------------------------------------------------------------

Principle: let the cheap local model do narrow, fixed-format work and spend
API tokens only where the larger model's quality matters. Beacon implements
this for grading (preparation/practice.py, grade_written):

  Written answer
     |
     v
  [1] Local Qwen2.5-1.5B screens it            (free, 0.7-1.4 s measured)
      -> {"on_topic": bool, "substantive": bool, "score": 0-100}
     |
     |-- off topic or too thin --> Beacon's rules write the feedback.
     |                             The API is never called.
     v
  [2] Hosted API (gpt-oss-20b) writes the real feedback and grade.
     |
     |-- API down / rate limited --> use the local provisional score.
     v
  [3] Validate the JSON, save the attempt, move the skill rating by at
      most 40% of the way to the new score.

Why each stage is where it is:
  - Screening is a classification job, where the lab put Qwen2.5-1.5B
    at 0.93 vs 1.00 for 4B models: near-equal quality for free.
  - Feedback is open-ended writing, where quality still rose with size,
    so it goes to the bigger model.
  - The local score never overrides the API's grade. The lab showed small
    models are lenient on weak answers, so it is only a fallback.

What it saves (estimate). Only grading can be screened; advice and coach
questions always go to the API. At 10,000 users that is 20,000 grading calls
a day at ~$0.00007-0.00011 each:

  Share of answers stopped by the screen   Saving per month
  30%                                      ~$12-20
  60%                                      ~$25-40

Against that, screening costs 3.9-7.8 hours of model time a day
(20,000 x 0.7-1.4 s), a machine to hold the model, and 0.7-1.4 s more on
every graded answer.

So at today's prices the hybrid is not mainly a money saver. Its value:
  - Resilience: grading still works when the API is down or rate limited.
  - Privacy: empty or off-topic text never leaves our server.
  - Price protection: if API prices rise, more work can move to the
    screen without code changes (LOCAL_LLM_MODEL swaps the model).

Other hybrid splits Beacon could add, same principle:
  - Route by job: extraction from resumes and tagging go local; advice
    and chat go to the API.
  - Cache by input: identical requests (same profile, same answer) are
    served from cache, as advice already is.


--------------------------------------------------------------------------------
4. COST COMPARISON: OWN SERVER VS PAID API
--------------------------------------------------------------------------------

Scenario: we buy a server with a 16-core CPU, 16-core GPU, 64 GB RAM and a
1 TB disk and run a pre-trained model in Django.

What that server can do (estimate, scaled from our measurements):
  - 64 GB holds any model from the lab (largest 8 GB in bf16), several
    copies of a small one, or a ~20-30B model in 4-bit. 1 TB stores every
    model we tested (~57 GB) many times over.
  - A 16-core GPU has a little less compute than the 20-core laptop GPU
    we measured, so expect similar or slightly lower speeds: ~48 tok/s
    for Qwen2.5-1.5B, ~19 tok/s for 4B, one request at a time.
  - Cost: ~$2,000-3,000 to buy (estimate), ~$55-85/month over three
    years, plus ~$6/month of electricity (50 W, 24/7, $0.16/kWh).
    Total ~$60-90/month.

Break-even with the API (using section 2's ~$0.015-0.021 per user per
month): $60-90 / $0.015-0.021 = ~2,800-6,000 daily users.

But one such server realistically serves ~800 daily users with
Qwen2.5-1.5B and ~300 with a 4B model (section 1). It runs out of capacity
long before it becomes cheaper than the API.

The pre-trained model on our own server is acceptable when:
  [x] Data cannot leave our infrastructure (privacy law, contracts,
      sensitive resumes or HR data). This overrides cost.
  [x] Usage is small and steady: under ~500-800 daily users, or batch jobs
      (overnight grading, tagging) where waiting in a queue is fine.
  [x] The task is narrow and fixed-format, where a 1.5-4B model is
      nearly as good as a large one (our lab: 0.93-1.00).
  [x] The hardware is already owned, so the real extra cost is
      electricity: ~$0.05 per 1M tokens vs $0.30 for API output.
  [x] The network is unreliable or not allowed (offline or on-site use).

Switch to a paid API of comparable model size when:
  [x] Traffic is spiky or concurrent. One request at a time at ~0.7 s
      means 100 simultaneous users wait up to ~70 s for the last answer.
  [x] Daily users pass what one server can handle (~800 for 1.5B, ~300
      for 4B), because the next step is a second server or a GPU cluster.
  [x] The task needs open-ended writing or judgement, where larger
      models were still measurably better.
  [x] The host is small. PythonAnywhere's 512 MB cannot hold torch, so
      the deployed site runs the API with LOCAL_LLM_ENABLED off.
  [x] No one on the team can own servers: patches, model updates,
      monitoring, on-call.
  [x] The monthly token bill is below the server bill. For Beacon that is
      true at every scale we estimated: ~$150-215/month for 10,000 users
      vs ~$730-1,460 for GPU servers.

Either way, keep the rules-based fallback, so advice and grading still work
when whichever model we chose is unavailable.
