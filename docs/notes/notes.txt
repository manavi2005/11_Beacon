WEEK 3 - DATA MODEL & ADMIN
--------------------------------------------------------------------------------

Five models, mapping one-to-one onto the four proposed features:

  Skill              catalog of competencies Beacon can diagnose
  CandidateProfile   one user's career goal and timeline
  SkillAssessment    through-model: candidate x skill, with a score
  PreparationPlan    a time-boxed roadmap
  PlanTask           one action inside a plan

Decisions worth recording:

  - SkillAssessment is a through-model rather than a plain M2M, because the
    link between a candidate and a skill is never bare - it always carries a
    score and a date. That is the whole product.

  - CandidateProfile is separate from django.contrib.auth.User. User answers
    "who is logged in"; CandidateProfile answers "what are they preparing
    for". Our product questions will change; Django's auth table should not.

  - Skill uses on_delete=PROTECT from SkillAssessment so scored history can
    never be silently destroyed. PlanTask.skill uses SET_NULL instead - if a
    skill disappears, we want to keep the task and just forget the tag.

  - readiness_percent and completion_percent are properties, not columns.
    Derived numbers that are stored go stale; derived numbers that are
    computed cannot.

Open question: whether SkillAssessment should keep history (one row per quiz
attempt) instead of one current row per candidate-skill pair. Right now a
unique constraint enforces one row. Revisit when the progress tracker needs
to draw a trend line.

SECTION 1 - Structure and security

  Split settings implemented at beacon_core/settings/:
    base.py         shared configuration, loads .env
    development.py  DEBUG = True,  ALLOWED_HOSTS = 127.0.0.1 / localhost
    production.py   DEBUG = False, ALLOWED_HOSTS from DJANGO_ALLOWED_HOSTS

  base.py is never run directly. manage.py defaults to the development
  module; production is selected with DJANGO_SETTINGS_MODULE.

  Secrets: SECRET_KEY and ALLOWED_HOSTS are read from .env, which is listed
  in .gitignore and has never been committed. .env.example is committed so a
  teammate cloning the repo knows exactly which keys to supply.

  base.py has a small hand-written load_env() rather than python-dotenv, so
  the project runs with nothing installed except Django.

SECTION 2 - Views

  Four views, one of each required kind. Each is marked in views.py with the
  number below, and each has a named URL route.

  View 1 | FBV, HttpResponse   | skill_catalog_manual | /skills/manual/
         | Fetches the template with loader.get_template(), renders it to a
         | string, wraps that string in HttpResponse. Purpose: show the skill
         | catalog while spelling out every step render() normally hides.

  View 2 | FBV, render()       | skill_catalog_render | /skills/
         | Same template, same data, one line instead of three. Purpose: the
         | everyday way we will write list pages for the rest of the project.

  View 3 | CBV, base View      | PlanBoardView        | /plans/cbv-base/
         | Inherits django.views.View. get() queries PreparationPlan by hand,
         | builds the context by hand, calls render() by hand. Purpose: show
         | all preparation plans, and show what a CBV does NOT give you for
         | free.

  View 4 | CBV, generic        | PlanTaskListView     | /tasks/
         | ListView with model = PlanTask, template_name, context_object_name
         | and paginate_by. Purpose: list every task across every plan - the
         | data behind Screen 4's progress tracker.

  Extra (not graded): PlanTaskDetailView, a generic DetailView at
  /tasks/<pk>/, linked from the task list.

  All routes are namespaced under app_name = "preparation" and every one has
  a name=, so templates reverse them instead of hard-coding paths.

SECTION 3 - Templates

  base.html holds {% block title %}, {% block heading %} and
  {% block content %}, plus the site navigation. Every page extends it.

  skill_list.html is rendered by BOTH function-based views. That reuse is the
  point: if the two FBVs produced visibly different pages, the difference
  between HttpResponse and render() would look bigger than it is.

  Every list template uses {% for %} with an {% empty %} branch carrying a
  message that says what to do next, not just "no results".

  Empty state: skill_list.html accepts an optional ?q= filter, so
  /skills/?q=zzzz produces a genuinely empty queryset for a screenshot
  without deleting any rows from the database.

SECTION 2 BONUS - WHEN EACH KIND OF VIEW WAS ACTUALLY USEFUL
--------------------------------------------------------------------------------

HttpResponse vs render()

  Writing the HttpResponse version first was what made render() make sense.
  Three steps are visible: find the template, hand it a context and get a
  string back, put that string inside an HTTP response. render() does exactly
  those three things. Before writing it out, render() felt like magic; after,
  it just felt like a shortcut.

  Where the manual form would genuinely earn its place in Beacon: anywhere we
  need to touch the response object itself rather than just its body - setting
  a content type for a plan exported as CSV, attaching a Content-Disposition
  header for a resume download, returning a non-200 status. render() hands
  back a finished response and assumes we want the defaults.

  For every ordinary page, render() wins. The manual version is three extra
  lines that can only go wrong.

Base CBV vs Generic CBV

  The base View gave us one thing over a function: dispatch by HTTP method.
  A GET lands in get(), a POST would land in post(), with no branching on
  request.method. That will matter for the assessment screen, where the same
  URL shows a question and receives an answer.

  Everything else was still our job. PlanBoardView writes its own queryset,
  its own context dictionary, its own render() call - which is essentially
  what the function-based view did, in a class.

  The generic ListView was a different experience. model = PlanTask was the
  whole configuration; the queryset, the context and the pagination came for
  free. We overrode get_queryset() only to add select_related(), and
  get_context_data() only to pass the teaching label.

  Our conclusion: generic CBVs when the page is a standard list or detail of
  one model, which is most of Beacon's read-only screens. Base View when the
  page is doing something Django has no generic for - the adaptive assessment,
  which chooses the next question based on previous answers, is not a
  ListView and pretending it is would cost more than writing get() ourselves.

  The trap with generic CBVs is that the logic is in method overrides spread
  across a class hierarchy you cannot see. When we found ourselves overriding
  three methods, writing the base View was clearer.

SECTION 1 - URL linking and navigation

    Implemented on Skill, CandidateProfile, PreparationPlan and PlanTask.
    Each returns reverse("preparation:<name>_detail", args=[self.pk]).

  End-to-end flow:
    /insights/ is the clearest demonstration. models.py supplies all five
    models and their relationships, urls.py maps the route, views.py runs the
    aggregations, and insights.html renders them - with every row linking back
    out through get_absolute_url().


WHERE get_absolute_url() IS ACTUALLY USEFUL IN BEACON
(required deliverable)

  The honest answer is that on a page that lists one kind of object, it saves
  very little. {% url 'preparation:skill_detail' skill.pk %} is not much worse
  than {{ skill.get_absolute_url }}.

  It starts paying off on the pages that mix object types. The insights page
  lists tasks, and each row links to the task, the skill it targets, and the
  candidate it belongs to - three different detail routes in one table. With
  {% url %} the template has to know the route name for each. With
  get_absolute_url() each object answers for itself, and the template just
  asks.

  The feature where it will matter most is the roadmap (Screen 3). That screen
  shows a week of mixed recommended items - a practice task, a skill to review,
  a mock interview to schedule. Those are different models today and there will
  be more of them later. If the template loops over one combined list and calls
  {{ item.get_absolute_url }}, adding a new kind of recommendation means adding
  one method to one model, and the roadmap template does not change at all.
  With {% url %} in the template, every new recommendation type means another
  {% if %} branch in the loop.

  The second reason is that the route name stops leaking into the templates.
  Right now the skill detail route is "preparation:skill_detail". If we split
  the app into per-feature apps as planned (profiles, diagnostics,
  mock_interviews, progress), that namespace changes. With get_absolute_url()
  the change is one line per model. Without it, it is a search-and-replace
  across every template that ever linked to a skill.

  Django itself already uses it: the admin's "View on site" button and the
  redirect after a successful CreateView both call get_absolute_url() when it
  exists. Implementing it gets that behaviour for free.


SECTION 2 - ORM queries and data presentation

  Basic query:
    CandidateListView lists CandidateProfile, annotated per row.

  Two search forms, and why each uses the method it does:

    GET  - /search/skills/
           Filters: name__icontains, category__exact, and a relationship span
           through assessments__candidate__target_role__icontains.
           The skill catalog is public reference data. A filtered view of it is
           worth sharing, bookmarking and reloading, so the filter belongs in
           the URL: /search/skills/?q=sql&category=TECH can be pasted into a
           team chat and it reproduces exactly what the sender saw. GET is
           right here precisely because the query is visible.

    POST - /search/candidates/
           Candidate records carry real names, email addresses, and the role
           somebody is quietly job-hunting for. A GET search would write that
           straight into the URL bar, the browser history, the server access
           log, and any link or screenshot the user later shares. POST keeps
           the term in the request body instead.

           Worth being precise: POST is not encryption. Both methods travel the
           same wire and only HTTPS protects either one in transit. What POST
           avoids is personal data being recorded in places that outlive the
           request.

           The cost is real. A POST result cannot be bookmarked, shared, or
           reloaded without the browser re-submitting. That is exactly the
           behaviour we want on the candidate lookup and exactly the behaviour
           we do not want on the catalog. The two pages link to each other so
           the contrast is visible side by side.

  Relationship spanning (Django field lookups with __):

    skill_search:      assessments__candidate__target_role__icontains
                       Skill -> SkillAssessment -> CandidateProfile, one query.

    candidate_search:  user__first_name, user__last_name, user__username,
                       user__email, all OR-ed with Q objects.
                       CandidateProfile -> User.

    insights:          plan__candidate__target_role__icontains
                       PlanTask -> PreparationPlan -> CandidateProfile.

  Aggregations:

    Total (count):
      Skill.objects.count(), PlanTask.objects.count(), and a filtered total
      PlanTask.objects.filter(status=DONE).count().

    Grouped summary (values + annotate):
      Skill.objects.values("category").annotate(skill_count=Count("id"))
      One row per category rather than one per skill - values() sets the
      GROUP BY column and annotate() is the aggregate over each group.

    Grouped summary with a filtered count:
      PreparationPlan.objects.annotate(
          task_total=Count("tasks", distinct=True),
          task_done=Count("tasks", filter=Q(tasks__status=DONE), distinct=True))
      Total and completed tasks per plan, in one query instead of one query
      per plan.

    Grouped average across a relationship:
      Skill.objects.annotate(average_proficiency=Avg("assessments__proficiency_score"))
      Sorted ascending, this is "which skills is our whole user base weakest
      at" - the question the plan generator will eventually need answered.

  Something that cost us time: distinct=True on Count.
    Annotating two different related tables in the same queryset makes the SQL
    join multiply rows, and the counts come back inflated. Adding distinct=True
    to each Count fixes it. Worth remembering, because the wrong numbers look
    perfectly plausible - nothing errors, the totals are just too big.

  Templates:
    Every table uses {% for %} with an {% empty %} branch, and every empty
    message says what to do next rather than only reporting that nothing was
    found.

    All multi-line template comments use {% comment %}...{% endcomment %}.
    Django's {# #} is single-line only - a multi-line one renders literally
    onto the page, which is the bug the smoke tests now guard against.

(required deliverable)

STATIC FILE ORGANIZATION: WHY PROJECT LEVEL

  Django looks for static files in two places: each app's own static/
  folder, found by AppDirectoriesFinder, and whatever directories are
  listed in STATICFILES_DIRS, found by FileSystemFinder. Both finders
  stay switched on. The question was only where to put ours.

  We put them at project level, in a top-level static/ next to manage.py:

    static/
      css/beacon.css        the whole site stylesheet
      img/beacon-logo.svg   lighthouse mark, logo and favicon

  The reason is ownership. beacon.css styles base.html, which every page
  in the project extends, and the logo is the product's, not any one
  feature's. Neither belongs to the preparation app. Putting them in
  preparation/static/ would say they do, and the day we split the work
  into profiles, diagnostics and progress as planned, those apps would be
  reaching into a sibling app's folder for the site stylesheet. That is
  the kind of dependency that is easy to create and annoying to undo.

  App-level static/ is still right for anything only one app uses. If the
  diagnostics quiz ends up needing its own JavaScript, it goes in
  diagnostics/static/diagnostics/, namespaced under the app name so two
  apps can both ship a file called quiz.js without colliding.

  The third directory is staticfiles/, which is STATIC_ROOT. Nothing is
  written there by hand. collectstatic gathers STATICFILES_DIRS and every
  app's static/ into it for deployment, so it is build output and it is
  git-ignored, the same way we do not commit .venv.

  One thing worth knowing: templates never write /static/ literally.
  {% static "css/beacon.css" %} builds the URL from STATIC_URL, which is
  what lets production swap in the hashed filename below without a single
  template changing.


CACHE BUSTING

  The problem. Static files want a long cache lifetime, because making a
  browser re-download an unchanged stylesheet on every page view is pure
  waste. But a long lifetime and a fixed filename are a bad combination.
  Ship a fix to beacon.css and every browser that already cached the old
  copy keeps serving it until the cache expires, which could be weeks. The
  user sees a half-styled page and "try a hard refresh" becomes the
  support answer. Shortening the cache lifetime fixes staleness by giving
  up the caching, which is trading the whole benefit for the fix.

  What we did. production.py sets the staticfiles backend to
  ManifestStaticFilesStorage. collectstatic then hashes the contents of
  each file into its name:

    css/beacon.css  ->  css/beacon.a0c1fb82e482.css

  and writes staticfiles.json mapping every plain name to its hashed one.
  {% static %} reads that manifest, so the template still names the file
  the readable way and the served URL carries the hash.

  Why that solves it. The filename is now derived from the content. Change
  one line of CSS and the hash changes, so the URL changes, and a URL the
  browser has never seen cannot be answered from cache: it has to fetch.
  Nothing expires early and nothing stale is served, so the cache lifetime
  can safely be set to a year. We verified it rather than assuming:

    collectstatic                -> beacon.a0c1fb82e482.css
    append one comment to the CSS
    collectstatic                -> beacon.f1aecec1ef47.css
    revert the comment
    collectstatic                -> beacon.a0c1fb82e482.css

  Development deliberately does not use it. runserver serves straight out
  of static/, an edit shows up on the next reload, and there is no
  manifest to keep in step. Turning it on in development would mean
  running collectstatic after every CSS change.

  Gotcha for later: with this backend, {% static %} raises an error if a
  file is missing from the manifest. So a deployment has to run
  collectstatic before it serves anything, and a path typo becomes a loud
  failure at deploy time rather than a silent 404 in the browser. That is
  the behaviour we want, but it is worth knowing before the first deploy.


WHAT THE STYLING ACTUALLY CHANGED

  Before this, base.html carried a <style> block of about 25 lines and
  every page shipped its own copy of it. Now there is one beacon.css.

  The visible changes, and why each one:

    Masthead. Navy band with the lighthouse mark and wordmark, so the
    site's identity is separated from the page content under it.

    Navigation. Ten items is too many for a row of underlined links, so
    they are pills with a real hit area that wrap tidily on a phone.

    Content card. White surface on a grey page, which gives the content
    an edge instead of floating.

    Tables. Most of this site is tables, so they got the most attention:
    zebra striping, uppercase column headers, a hover row, and rounded
    clipping. A 24-row task list is readable now.

    Stat tiles. The totals on the dashboard and the insights page were
    two-column tables, which is a lot of chrome for six numbers. They are
    tiles now, with the number set large.

    Progress meters. Plan completion shows a bar next to the percentage,
    because a proportion is easier to compare as a length than as digits.

    Status pills. Colour-coded, but the word still says Done or Active on
    its own. Colour is a second signal, never the only one.

    Colours. The university's navy and orange. Navy carries structure,
    orange is reserved for things you can act on, which is why links and
    the stat tile accent are orange and headings are not.

    Fonts. A system font stack, so there is no network request for a web
    font and the page renders in the typeface the reader's OS already
    uses for its own interface.

  It reflows to one column under 700px, and the wide tables scroll
  sideways inside their own box rather than crushing six columns into a
  phone width. There is also a print stylesheet that drops the nav and
  the footer, since a plan or task list is a plausible thing to print.

  Tests: 6 added, checking that static/ is on the search path, that the
  finders can resolve the CSS and the logo, that base.html links the
  stylesheet through {% static %}, that every page carries it, and that no
  inline <style> block has crept back in. 31 total, all passing.
